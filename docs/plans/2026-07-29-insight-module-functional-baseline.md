## 1. 模块要回答的问题

> **过去哪些素材在什么条件下有效或失效，下一次应该如何创作和投放？** 〔03 §1〕

模块由两条链构成：

```
投前链：历史素材 + 已确认经验 + 行业受众证据 → 投前洞察 → 支持 Brief/策略/脚本/创意
投后链：投放数据 → 投后分析 → 内容与效果归因 → 复盘报告 → 经验沉淀 → 回流投前
```

**明确的非目标**〔03 §2〕：不做通用云盘；不以文件夹/版权审批/存储生命周期为核心；**不做脱离上下文的全局排行榜**；不承诺"历史表现好就下次有效"；不自动删除或替换真实投放素材。

## 3. 全模块通用契约

### 3.1 洞察卡九字段〔03 §8.1〕

任何洞察卡缺字段即不合格：

| 字段 | 说明 |
| --- | --- |
| 结论 | 一句可执行描述 |
| **类型** | **事实 / 统计观察 / 假设 / 建议**——四者不可混淆 |
| 适用范围 | 品牌、产品、渠道、广告类型、目标、受众、时间 |
| 数据依据 | 素材数量、样本、时间窗口、指标、对比基线 |
| 内容依据 | 关键素材特征与示例版本 |
| 置信提示 | 充分 / 方向性 / 样本不足 / 存在混杂 |
| 风险与反例 | 可能不适用的条件 |
| 建议动作 | 用于策略、创意或投放的下一步 |
| 状态 | 待确认 / 已确认 / 待复审 / 已失效 |

> 「类型」字段承载 03 §2 目标⑥：**保留事实、计算、推断和人工结论的边界，避免把相关性误写成因果**。这是本模块与普通报表工具的根本区别。

### 3.2 防误读机制〔03 §10.3〕

1. 样本不足、窗口过短、归因延迟时**显著提示**
2. **跨渠道或跨目标比较默认关闭**，用户显式开启后展示口径差异
3. 数据异常时**暂停生成强结论**，先建议检查追踪、匹配和同步

### 3.3 四层数据分离〔03 §14〕

**原始事实 / 计算结果 / AI 推断 / 人工结论分别存储，不相互覆盖。**
金额用定点数带币种；时间保留平台时区与 UTC。

### 3.4 可追溯〔03 §MVP⑫、§12〕

任一分析结论都能回溯到：素材版本 · 数据截止时间 · 指标版本 · Skill/算法版本。
AnalysisRun 固化输入快照、查询条件、方法、版本和结果哈希，指标计算可重放。

### 3.5 分析状态链〔03 §11.1〕

```
待数据 → 待匹配 → 可分析 → 分析中 → 待确认 → 已确认 / 待复审 / 已失效
```

### 3.6 页面契约〔22 §8.2 §8.3、20 §7〕

- 页头显示 `Project 名称 / 工作台阶段 / 模块 / 页面或对象`，Project 和阶段可点击
- **不重复显示八阶段流程图**
- 集合页用集合路由；详情页**必须包含对象 ID**
- **每个可见 L2 标签必须真实改变数据集、工作区或对象状态**；只改文字或高亮不算实现
- **未实现的功能隐藏入口，不显示永久禁用的空页面**
- 演示数据必须明确标识〔22 §12.3〕
- 所有 P0 页面须有：加载 / 空 / 错误 / 无权限 / 版本冲突 / 部分成功 六种状态〔22 §9.3〕

### 3.7 权限与角色〔03 §11.2、20 §4.2〕

- 权限动作用 `insights.*`，查看 / 口径配置 / 经验确认分别授权
- 普通成员不能修改原始事实；确认组织经验需指定角色
- 默认导航按角色：策略创意角色见投前洞察/分析素材库/内容分析/经验库；分析投放角色见投后分析/内容分析/报告中心/经验库；数据角色加数据接入/数据质量

## 4. 建设顺序〔20 §6.1〕

20 号文档给的是跨模块顺序，映射到素材洞察 11 个功能：

| 批次 | 本模块对应功能 | 20 §6.1 给的原因 |
| --- | --- | --- |
| 1 | **分析素材库**（＋数据接入作为其前提¹） | 先建立稳定业务容器、状态和版本 |
| 2 | **内容分析 · 投后分析** | 完成模块不可替代的主要任务 |
| 3 | **数据质量** | AI 与自动执行上线前必须具备 |

### 7.7.3 第 5 批：数据质量（2026-07-29 深夜）

**一句话：** 质量问题**不入库**，每次请求实时算出；入库的只有「人做了什么判断」。

这是这一批唯一需要记住的设计决定。如果问题本身也入库，就会出现「库里说坏了、数据说已经好了」
这种自相矛盾的状态——一个数据质量模块最不该有的毛病。所以新表
`insight_quality_dispositions`（`migrations/insights/20260729163000_insight_data_quality.up.sql`）
只有处置记录，一条问题在一个 Project 里只有一行，再次处置是覆盖并抬高 `version`。

| 功能 | 动工前 | 现在 | 仍缺 |
| --- | --- | --- | --- |
| 数据质量 | 0 / 6（占位页） | 6 个视图全部真实 | 无外部对账源（口径与对账只比库内数据）；无告警推送 |

**五类检测器**（`internal/systems/insights/quality.go`，权威源）：

| 类型 | 检什么 | 阈值 |
| --- | --- | --- |
| freshness 新鲜度 | 已启用数据源的数据截止日 | 滞后 > 2 天警告，> 4 天阻断 |
| missing 缺失 | 窗口内日期空洞、导入被拒的行 | 只在数据实际覆盖的区间内判空洞 |
| anomaly 异常 | 人工标记的质量状态、物理上不可能的值（如点击 > 曝光） | 不可能值一律阻断 |
| caliber 口径 | 币种 / 归因窗口 / 指标版本在一个窗口里是否混了 | 混了才报 |
| reconciliation 对账 | 花费能不能归到素材上 | 映射率 < 80% 阻断，< 95% 警告 |

**三个不显然但必要的点：**

1. **`observed_through`**：处置时记下该问题当时的最新观测时间。之后若出现更晚的观测，
   `resolved` 自动翻成 `reopened`。没有它，点一次「已修复」就能把问题永久藏起来。
   新鲜度问题的观测时间就是「现在」——所以数据还滞后时标已修复会**立刻**弹回，这是有意的。
2. **`fingerprint(kind, slot, scope)` 不含数据窗口**：换个窗口看同一个问题，处置仍然跟得住。
3. **任一阻断问题 ⇒ `StrongConclusionsAllowed = false`**（PRD §10.3 / doc10 §12.4）。
   已忽略的不算——那是有人明确判过「跟我无关」。

### 7.7.5　第 7 批：投后分析补齐五个视图（2026-07-29）

`internal/systems/insights/performance.go` + `src/components/PostLaunchAnalysisPage.tsx`。
指标总览留在原页（20 §4.1 要求它是「一个主图表 + 素材矩阵 + 解释区」，和另外五个列表视图不是同一种页面），
新增素材对比 / 趋势 / 疲劳 / 异常 / 驱动因素五个视图，共用一次 `GET …/performance-analysis` 返回。
**五个视图共用一次请求是有意的**：拆成五次读取后，「趋势里看到的」和「疲劳里算的」会来自两次快照，
对不上时没人解释得清。

这一批真正的内容是**一套关于「能不能下结论」的判定**，不是五个图表：

- **归因阶梯（AM-009）**。`可归因 / 只能看方向 / 归不了因 / 样本不足 / 缺内容特征` 五档里，只有第一档
  是「这个差异能算到这个变量头上」，后四档都是「不能」，区别只在为什么不能。同时改了两个变量的一对，
  数字差 80% 也只能是「归不了因」。
- **疲劳要列出没排除的解释（03 §7.4）**。代码只列「排除不了的」，不写「已排除」。**受众变化永远列在里面**——
  受众构成数据一条都没接入，人群变了和素材看腻了在数字上长得一样。
- **天数不够时置信必须压到 `low_sample`**。修过一个真实缺陷：3 天数据时后端返回「没有疲劳迹象 + 置信充分」，
  页面上读作「查过了，没问题」，而事实是「压根没法查」。这两句话对读者意义相反。
- **用 MAD 不用标准差**。一次大促尖峰会把标准差自己抬高，之后什么都不再异常。
- **异常看两个尺度**。项目级花费抓「今天整体花超了」，素材级曝光抓「某条素材昨天被转了一次」——
  后者会被其余素材的量摊平在总数里，而它恰恰是解释单条素材表现时最先要排除的。
  同一素材同方向多天命中时只报最极端那天，备注挑明「多半是投放量整体变过一次，不是那天出事」：
  整窗中位数对台阶不稳健，逐条列出来会把一件事说成十几件事。
- **驱动因素的门槛是 4 个同类型素材**（`minDriverAssets*2`）。不足 4 个时任何分组都退化成「一个对一个」，
  那是素材对比不是驱动因素。一个特征只有两个取值时只出一行——两行是同一句话的正反两面。

页面固定挂一句边界：这里全部是观察到的相关，没有一条是实验证明的因果；要确认得只改一个变量再投一轮，
那是实验中心的事，当前还没有开。

**演示数据**：`scripts/seed-insight-performance-demo.sh`（四条刻意设计的曲线：v2 疲劳形态、v1 平稳、
长文一天冲高一天断档、v1 补投）和 `scripts/seed-insight-drivers-demo.sh`（再补 v3/v4，钩子类型才凑得出
2 对 2 的对照）。两个脚本都走真实导入接口而不是直接写库，落库路径、口径校验、未匹配对象入队跟着一起验证。
基线曲线要带正常抖动：写成每天恰好 4000 反而测不出东西，异常检测遇到零波动序列会直接跳过。

**遗留：**

- 驱动因素的对照组目前只有 4 个素材，是够门槛的最小规模。真实项目素材更多时，这一页的排序和降噪
  需要再看一轮。
- 素材级异常只看曝光。花费还受出价和预算分配影响，等有了投放动作日志再考虑加。
- 项目级异常仍是整窗 MAD，没有做台阶收敛（素材级做了）。项目总量的台阶通常对应真实的预算调整，
  但目前没有验证过。

### 7.7.6　第 8 批：能力运营五个视图（2026-07-29）

`internal/systems/insights/operations.go` + `src/components/CapabilityOperationsPage.tsx`。
特征体系 / 指标字典 / 分析 Skills / 评测集 / 质量看板五个视图，共用一次
`GET …/capability-operations` 返回。冲突 11 同批消解（第五个视图名按文档改成「质量看板」）。

**一张新表都没建，这是这一批最重要的决定。** 五个视图的数据全部从 `insight_assets`、
`insight_asset_features`、`insight_data_sources`、`insight_metric_daily` 现算：特征体系读的是
`features.go` 里的六套 schema，指标字典是代码里声明的常量，Skill 与评测集从已有的特征行统计。
存一份治理台账，它迟早会和它治理的数据对不上——而治理面对不上，比业务页面对不上更难发现，
因为没有第二个地方可以对照。同理，整页**只读**：口径和词表要改就改代码、过评审、留版本
（03 §14 要求口径变更之后必须能重算，且不能悄悄改写已经发出去的历史结论）。

这一批真正的内容是**四条「不许自我美化」的约束**，都写成了测试：

- **取值分布必须用生效值**（`TestHumanConclusionReplacesAIValueInVocabularyStats`）。同一条素材上
  人工结论覆盖机器结论（03 §14），机器的旧值不再计入。否则「机器写 A、人改成 B」会被数成两个取值，
  词表看上去比实际更碎，而碎掉的那一半根本没人在用。
- **准确率有样本门槛，且不是独立评测集**（`TestEvaluationWithFewSamplesRefusesToReportAccuracy`、
  `TestUnreviewedExtractionsAreNotCountedAsCorrect`）。样本只来自人工复核记录，
  没人看过的提取一条都不算。把它们算成「机器对了」，准确率会随提取量自动上涨，
  而那个上涨和模型好不好毫无关系。不足 10 条时直接不给数字。
- **一致按取值文本判，不看复核状态**（`TestRejectedReviewCountsAsDisagreementEvenWithSameValue`）。
  `PatchFeatures` 把人工行的复核状态默认成「已确认」，拿它当「认可了机器」会把改写数成一致。
- **派生指标只能总量除总量**（`TestDerivedMetricUsesTotalsNotDailyAverage`）。曝光量差别大的两天，
  日均比率和真实比率能差好几倍，而那个差值没有任何业务含义。页面上派生指标也不写「合计」，
  写「窗口值」——这一页正是在说比率不能相加。

另有两条边界：

- **待归并只是候选，且只对 enum / enum_multi / tags 统计**。这三类的取值本该收敛到一组共用词，
  出现一次才说明有东西；`text` 每条都不一样是它的设计意图，`number` / `bool` / `duration` 的
  「单次取值」更是没有含义。**这是实测发现的缺陷**：接真实数据时「痛点」（text）和「AI 标识」（bool）
  都被报成了待归并，队列会被必然唯一的值塞满，真正在散的枚举反而看不见。修完候选数从 4 降到 2。
  即便如此它仍然只是候选，不进待办队列——把两个真正不同的取值合并，比词表碎一点更糟。
- **词表待办只列已经有人用的字段**（`TestUnusedOpenVocabularyFieldsStayOutOfTheTodoList`）。
  六套 schema 里没发布词表的字段有 73 个，但没人填过的字段散不散没有影响。

**修过的第二个真实缺陷**：空列表被序列化成 JSON `null`（Go 的 nil 切片），前端取 `.length`
整页白屏。已在 `buildCapabilityOperations` 里补成 `[]` 并加了序列化测试
（`TestEmptyCapabilityOperationsSerializesToEmptyArrays`）。「没有口径冲突」是一个要被读出来的结论，
它得有个明确的零。

**遗留：**

- 评测集的诚实边界意味着它永远只能回答「人看过的那些」。要回答「整体准确率是多少」，
  得有一批独立抽样、且抽样规则和复核队列无关的样本——那需要新的抽样模型，本批没做。
- 「在用版本」按最近一次提取时间判，不按版本号排序（`TestLatestSkillVersionIsChosenByExtractionTime`
  钉住了这一点：v9 和 v10 按字符串比大小会得出 v9 更新的结论）。但如果两个版本并行在跑，
  「在用」这个说法本身就不够用了，得改成按素材维度看。
- 口径冲突只检查数据源之间。同一个数据源改过口径（`metric_schema_version` 升级）的历史数据，
  当前算不出来——那需要指标行上带口径版本，`insight_metric_daily` 现在没有这一列。
