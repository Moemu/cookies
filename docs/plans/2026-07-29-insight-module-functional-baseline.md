## 1. 模块要回答的问题

> **过去哪些素材在什么条件下有效或失效，下一次应该如何创作和投放？** 〔03 §1〕

模块由两条链构成：

```
投前链：历史素材 + 已确认经验 + 行业受众证据 → 投前洞察 → 支持 Brief/策略/脚本/创意
投后链：投放数据 → 投后分析 → 内容与效果归因 → 复盘报告 → 经验沉淀 → 回流投前
```

**明确的非目标**〔03 §2〕：不做通用云盘；不以文件夹/版权审批/存储生命周期为核心；**不做脱离上下文的全局排行榜**；不承诺"历史表现好就下次有效"；不自动删除或替换真实投放素材。

## 3. 全模块通用契约

### 3.1 洞察卡九字段〔03 §8.1〕

任何洞察卡缺字段即不合格：

| 字段 | 说明 |
| --- | --- |
| 结论 | 一句可执行描述 |
| **类型** | **事实 / 统计观察 / 假设 / 建议**——四者不可混淆 |
| 适用范围 | 品牌、产品、渠道、广告类型、目标、受众、时间 |
| 数据依据 | 素材数量、样本、时间窗口、指标、对比基线 |
| 内容依据 | 关键素材特征与示例版本 |
| 置信提示 | 充分 / 方向性 / 样本不足 / 存在混杂 |
| 风险与反例 | 可能不适用的条件 |
| 建议动作 | 用于策略、创意或投放的下一步 |
| 状态 | 待确认 / 已确认 / 待复审 / 已失效 |

> 「类型」字段承载 03 §2 目标⑥：**保留事实、计算、推断和人工结论的边界，避免把相关性误写成因果**。这是本模块与普通报表工具的根本区别。

### 3.2 防误读机制〔03 §10.3〕

1. 样本不足、窗口过短、归因延迟时**显著提示**
2. **跨渠道或跨目标比较默认关闭**，用户显式开启后展示口径差异
3. 数据异常时**暂停生成强结论**，先建议检查追踪、匹配和同步

### 3.3 四层数据分离〔03 §14〕

**原始事实 / 计算结果 / AI 推断 / 人工结论分别存储，不相互覆盖。**
金额用定点数带币种；时间保留平台时区与 UTC。

### 3.4 可追溯〔03 §MVP⑫、§12〕

任一分析结论都能回溯到：素材版本 · 数据截止时间 · 指标版本 · Skill/算法版本。
AnalysisRun 固化输入快照、查询条件、方法、版本和结果哈希，指标计算可重放。

### 3.5 分析状态链〔03 §11.1〕

```
待数据 → 待匹配 → 可分析 → 分析中 → 待确认 → 已确认 / 待复审 / 已失效
```

### 3.6 页面契约〔22 §8.2 §8.3、20 §7〕

- 页头显示 `Project 名称 / 工作台阶段 / 模块 / 页面或对象`，Project 和阶段可点击
- **不重复显示八阶段流程图**
- 集合页用集合路由；详情页**必须包含对象 ID**
- **每个可见 L2 标签必须真实改变数据集、工作区或对象状态**；只改文字或高亮不算实现
- **未实现的功能隐藏入口，不显示永久禁用的空页面**
- 演示数据必须明确标识〔22 §12.3〕
- 所有 P0 页面须有：加载 / 空 / 错误 / 无权限 / 版本冲突 / 部分成功 六种状态〔22 §9.3〕

### 3.7 权限与角色〔03 §11.2、20 §4.2〕

- 权限动作用 `insights.*`，查看 / 口径配置 / 经验确认分别授权
- 普通成员不能修改原始事实；确认组织经验需指定角色
- 默认导航按角色：策略创意角色见投前洞察/分析素材库/内容分析/经验库；分析投放角色见投后分析/内容分析/报告中心/经验库；数据角色加数据接入/数据质量

## 4. 建设顺序〔20 §6.1〕

20 号文档给的是跨模块顺序，映射到素材洞察 11 个功能：

| 批次 | 本模块对应功能 | 20 §6.1 给的原因 |
| --- | --- | --- |
| 1 | **分析素材库**（＋数据接入作为其前提¹） | 先建立稳定业务容器、状态和版本 |
| 2 | **内容分析 · 投后分析** | 完成模块不可替代的主要任务 |
| 3 | **数据质量** | AI 与自动执行上线前必须具备 |

### 7.7.3 第 5 批：数据质量（2026-07-29 深夜）

**一句话：** 质量问题**不入库**，每次请求实时算出；入库的只有「人做了什么判断」。

这是这一批唯一需要记住的设计决定。如果问题本身也入库，就会出现「库里说坏了、数据说已经好了」
这种自相矛盾的状态——一个数据质量模块最不该有的毛病。所以新表
`insight_quality_dispositions`（`migrations/insights/20260729163000_insight_data_quality.up.sql`）
只有处置记录，一条问题在一个 Project 里只有一行，再次处置是覆盖并抬高 `version`。

| 功能 | 动工前 | 现在 | 仍缺 |
| --- | --- | --- | --- |
| 数据质量 | 0 / 6（占位页） | 6 个视图全部真实 | 无外部对账源（口径与对账只比库内数据）；无告警推送 |

**五类检测器**（`internal/systems/insights/quality.go`，权威源）：

| 类型 | 检什么 | 阈值 |
| --- | --- | --- |
| freshness 新鲜度 | 已启用数据源的数据截止日 | 滞后 > 2 天警告，> 4 天阻断 |
| missing 缺失 | 窗口内日期空洞、导入被拒的行 | 只在数据实际覆盖的区间内判空洞 |
| anomaly 异常 | 人工标记的质量状态、物理上不可能的值（如点击 > 曝光） | 不可能值一律阻断 |
| caliber 口径 | 币种 / 归因窗口 / 指标版本在一个窗口里是否混了 | 混了才报 |
| reconciliation 对账 | 花费能不能归到素材上 | 映射率 < 80% 阻断，< 95% 警告 |

**三个不显然但必要的点：**

1. **`observed_through`**：处置时记下该问题当时的最新观测时间。之后若出现更晚的观测，
   `resolved` 自动翻成 `reopened`。没有它，点一次「已修复」就能把问题永久藏起来。
   新鲜度问题的观测时间就是「现在」——所以数据还滞后时标已修复会**立刻**弹回，这是有意的。
2. **`fingerprint(kind, slot, scope)` 不含数据窗口**：换个窗口看同一个问题，处置仍然跟得住。
3. **任一阻断问题 ⇒ `StrongConclusionsAllowed = false`**（PRD §10.3 / doc10 §12.4）。
   已忽略的不算——那是有人明确判过「跟我无关」。

**前端**（`src/components/DataQualityPage.tsx`）：六个视图共用一次请求。前五个按类型看**全部**
问题（含已处置的），第六个「修复队列」跨类型只留还需要人管的（待处理 / 跟进中 / 报修后又出现），
数据集确实不同（22 §8.3）。问题队列为主、错误与延迟置顶（20 §4.1）。

已在浏览器端到端验证：滞后 7 天的阻断问题出现在队列 → 标「跟进中」（version 1，仍在队列）→
标「已修复」（version 2）→ 下一次请求立刻翻成「报修后又出现」并回到队列。验证用的处置记录已清除。

**遗留：**

- doc10 §10 写的是 `GET /api/insights/v1/data-quality`（不带 project），实现挂在
  `/projects/{project_id}/data-quality` 下。理由：问题全部由某个 Project 的数据源和指标算出，
  不带 project 服务端得替调用方猜。**已登记为冲突 9。**

### 7.7.5　第 7 批：投后分析补齐五个视图（2026-07-29）

`internal/systems/insights/performance.go` + `src/components/PostLaunchAnalysisPage.tsx`。
指标总览留在原页（20 §4.1 要求它是「一个主图表 + 素材矩阵 + 解释区」，和另外五个列表视图不是同一种页面），
新增素材对比 / 趋势 / 疲劳 / 异常 / 驱动因素五个视图，共用一次 `GET …/performance-analysis` 返回。
**五个视图共用一次请求是有意的**：拆成五次读取后，「趋势里看到的」和「疲劳里算的」会来自两次快照，
对不上时没人解释得清。

这一批真正的内容是**一套关于「能不能下结论」的判定**，不是五个图表：

- **归因阶梯（AM-009）**。`可归因 / 只能看方向 / 归不了因 / 样本不足 / 缺内容特征` 五档里，只有第一档
  是「这个差异能算到这个变量头上」，后四档都是「不能」，区别只在为什么不能。同时改了两个变量的一对，
  数字差 80% 也只能是「归不了因」。
- **疲劳要列出没排除的解释（03 §7.4）**。代码只列「排除不了的」，不写「已排除」。**受众变化永远列在里面**——
  受众构成数据一条都没接入，人群变了和素材看腻了在数字上长得一样。
- **天数不够时置信必须压到 `low_sample`**。修过一个真实缺陷：3 天数据时后端返回「没有疲劳迹象 + 置信充分」，
  页面上读作「查过了，没问题」，而事实是「压根没法查」。这两句话对读者意义相反。
- **用 MAD 不用标准差**。一次大促尖峰会把标准差自己抬高，之后什么都不再异常。
- **异常看两个尺度**。项目级花费抓「今天整体花超了」，素材级曝光抓「某条素材昨天被转了一次」——
  后者会被其余素材的量摊平在总数里，而它恰恰是解释单条素材表现时最先要排除的。
  同一素材同方向多天命中时只报最极端那天，备注挑明「多半是投放量整体变过一次，不是那天出事」：
  整窗中位数对台阶不稳健，逐条列出来会把一件事说成十几件事。
- **驱动因素的门槛是 4 个同类型素材**（`minDriverAssets*2`）。不足 4 个时任何分组都退化成「一个对一个」，
  那是素材对比不是驱动因素。一个特征只有两个取值时只出一行——两行是同一句话的正反两面。

页面固定挂一句边界：这里全部是观察到的相关，没有一条是实验证明的因果；要确认得只改一个变量再投一轮，
那是实验中心的事，当前还没有开。

**演示数据**：`scripts/seed-insight-performance-demo.sh`（四条刻意设计的曲线：v2 疲劳形态、v1 平稳、
长文一天冲高一天断档、v1 补投）和 `scripts/seed-insight-drivers-demo.sh`（再补 v3/v4，钩子类型才凑得出
2 对 2 的对照）。两个脚本都走真实导入接口而不是直接写库，落库路径、口径校验、未匹配对象入队跟着一起验证。
基线曲线要带正常抖动：写成每天恰好 4000 反而测不出东西，异常检测遇到零波动序列会直接跳过。

**遗留：**

- 驱动因素的对照组目前只有 4 个素材，是够门槛的最小规模。真实项目素材更多时，这一页的排序和降噪
  需要再看一轮。
- 素材级异常只看曝光。花费还受出价和预算分配影响，等有了投放动作日志再考虑加。
- 项目级异常仍是整窗 MAD，没有做台阶收敛（素材级做了）。项目总量的台阶通常对应真实的预算调整，
  但目前没有验证过。

### 7.7.6　第 8 批：能力运营五个视图（2026-07-29）

`internal/systems/insights/operations.go` + `src/components/CapabilityOperationsPage.tsx`。
特征体系 / 指标字典 / 分析 Skills / 评测集 / 质量看板五个视图，共用一次
`GET …/capability-operations` 返回。冲突 11 同批消解（第五个视图名按文档改成「质量看板」）。

**一张新表都没建，这是这一批最重要的决定。** 五个视图的数据全部从 `insight_assets`、
`insight_asset_features`、`insight_data_sources`、`insight_metric_daily` 现算：特征体系读的是
`features.go` 里的六套 schema，指标字典是代码里声明的常量，Skill 与评测集从已有的特征行统计。
存一份治理台账，它迟早会和它治理的数据对不上——而治理面对不上，比业务页面对不上更难发现，
因为没有第二个地方可以对照。同理，整页**只读**：口径和词表要改就改代码、过评审、留版本
（03 §14 要求口径变更之后必须能重算，且不能悄悄改写已经发出去的历史结论）。

这一批真正的内容是**四条「不许自我美化」的约束**，都写成了测试：

- **取值分布必须用生效值**（`TestHumanConclusionReplacesAIValueInVocabularyStats`）。同一条素材上
  人工结论覆盖机器结论（03 §14），机器的旧值不再计入。否则「机器写 A、人改成 B」会被数成两个取值，
  词表看上去比实际更碎，而碎掉的那一半根本没人在用。
- **准确率有样本门槛，且不是独立评测集**（`TestEvaluationWithFewSamplesRefusesToReportAccuracy`、
  `TestUnreviewedExtractionsAreNotCountedAsCorrect`）。样本只来自人工复核记录，
  没人看过的提取一条都不算。把它们算成「机器对了」，准确率会随提取量自动上涨，
  而那个上涨和模型好不好毫无关系。不足 10 条时直接不给数字。
- **一致按取值文本判，不看复核状态**（`TestRejectedReviewCountsAsDisagreementEvenWithSameValue`）。
  `PatchFeatures` 把人工行的复核状态默认成「已确认」，拿它当「认可了机器」会把改写数成一致。
- **派生指标只能总量除总量**（`TestDerivedMetricUsesTotalsNotDailyAverage`）。曝光量差别大的两天，
  日均比率和真实比率能差好几倍，而那个差值没有任何业务含义。页面上派生指标也不写「合计」，
  写「窗口值」——这一页正是在说比率不能相加。

另有两条边界：

- **待归并只是候选，且只对 enum / enum_multi / tags 统计**。这三类的取值本该收敛到一组共用词，
  出现一次才说明有东西；`text` 每条都不一样是它的设计意图，`number` / `bool` / `duration` 的
  「单次取值」更是没有含义。**这是实测发现的缺陷**：接真实数据时「痛点」（text）和「AI 标识」（bool）
  都被报成了待归并，队列会被必然唯一的值塞满，真正在散的枚举反而看不见。修完候选数从 4 降到 2。
  即便如此它仍然只是候选，不进待办队列——把两个真正不同的取值合并，比词表碎一点更糟。
- **词表待办只列已经有人用的字段**（`TestUnusedOpenVocabularyFieldsStayOutOfTheTodoList`）。
  六套 schema 里没发布词表的字段有 73 个，但没人填过的字段散不散没有影响。

**修过的第二个真实缺陷**：空列表被序列化成 JSON `null`（Go 的 nil 切片），前端取 `.length`
整页白屏。已在 `buildCapabilityOperations` 里补成 `[]` 并加了序列化测试
（`TestEmptyCapabilityOperationsSerializesToEmptyArrays`）。「没有口径冲突」是一个要被读出来的结论，
它得有个明确的零。

**遗留：**

- 评测集的诚实边界意味着它永远只能回答「人看过的那些」。要回答「整体准确率是多少」，
  得有一批独立抽样、且抽样规则和复核队列无关的样本——那需要新的抽样模型，本批没做。
- 「在用版本」按最近一次提取时间判，不按版本号排序（`TestLatestSkillVersionIsChosenByExtractionTime`
  钉住了这一点：v9 和 v10 按字符串比大小会得出 v9 更新的结论）。但如果两个版本并行在跑，
  「在用」这个说法本身就不够用了，得改成按素材维度看。
- 口径冲突只检查数据源之间。同一个数据源改过口径（`metric_schema_version` 升级）的历史数据，
  当前算不出来——那需要指标行上带口径版本，`insight_metric_daily` 现在没有这一列。

### 7.7.7　第 9 批：AI 提特征（2026-07-29）

`internal/systems/insights/extraction.go`、`extraction_schema.go`、`skills/`、
`migrations/insights/…_insight_analysis_runs.up.sql`，前端在
`src/components/ContentAnalysisPage.tsx` 的「单素材拆解」里。三个端点：
`POST …/assets/{id}:analyze`、`GET …/assets/{id}/analysis-runs`、`GET …/analysis-runs`。

**在此之前，内容分析页上的特征全是人手工填的。** 六套特征体系、两层结论、复核动作
都已经有了，但没有任何东西会去「提」——AM-005 那一步是空的。这一批把它补上。

**模型的输出 Schema 是从特征体系生成的，不是手写的**（`featureOutputSchema`）。
03 §MVP② 把「不把视频钩子字段套到公众号文章」列为明文验收；靠提示词叮嘱模型
「请只回答本类字段」是守不住的，所以这里让它在结构上做不到——请求里带的
JSON Schema 就是这类素材自己那套字段，别类的字段名连出现的机会都没有
（`TestModelOnlyEverSeesItsOwnAssetTypesSchema`）。受控词表同样进 Schema 的 `enum`。

四条约束写成了测试：

- **模型输出只进 AI 那一层，状态停在待确认**（`TestExtractionWritesOnlyTheAILayerAndStopsForReview`）。
  doc09 §8：未经业务服务确认的模型输出不能直接成为已确认制品。提完之后页面上要逐项
  认可或推翻，人工结论仍然单独成行。
- **一条坏答案不能毁掉整批**。模型有时会返回受控词表以外的词（有的供应商把 Schema
  当事后校验）。原先这会让整次 `ExtractFeatures` 失败，另外十几条提对了的特征陪着一起丢。
  **这是实测发现的缺陷**：现在写入侧再过一遍校验，坏的那条被丢掉并带原因报出来
  （`AnalyzeAssetResult.dropped_fields`，页面上写「有 N 项没采信」），其余照常入库。
- **空结果记成失败，不记成「成功但没提到东西」**（`TestEmptyResultIsRecordedAsAFailureNotAnEmptySuccess`）。
  一次什么都没提到的调用，和一次报错的调用，对运营面是同一件事；记成成功会让
  §310 的成功率虚高。
- **没配模型就直接失败，不退化成模板产出**（`TestExtractionFailsInsteadOfFabricatingWhenNoModelIsConfigured`）。
  库里一条编造的特征，代价远大于一次失败的提取——它会被当成机器的判断进入复核队列。

任务留痕（`insight_analysis_runs`）按 03 §113/§304 的可追溯要求存全链路：Skill ID、
Skill 版本与内容哈希、提示词版本、供应商、模型别名与版本、路由版本、输入哈希、
结果哈希、token 数、耗时、丢弃字段、失败原因。**但不存输入正文**——只存它的哈希和
规模摘要（`asset_revision` / `content_chars` / `has_note` / `field_count`），
doc09 §7：日志默认不记录内容全文。失败的任务同样留一行，前端「数据与方法」里
成功失败一起列：只列成功的，成功率永远是 100%。

**触发方式是人点按钮，登记素材时不自动排队**（这是需求方定的）。复核是这套东西唯一的
质量闸门，自动排队会把队列灌满没人看得完的结果，闸门就形同虚设。所以整条链路上
没有任何地方会自己发起提取。

**遗留：**

- **素材正文不在库里**。`insight_assets` 存的是素材的身份和状态，不存正文，所以提取时
  正文必须由调用方带上（页面上就是那个必填的文本框）。副作用是：同一条素材换一份正文
  再提一次，系统看不出来这是两份不同的输入——只能事后比对 `input_hash`。
- **因此复现只能做到哈希比对，做不到重放**。要真正重跑一次历史任务，得把输入正文
  存在别处（素材库或对象存储）并在任务记录里引用，本批没做。
- **Insights 借用了 Strategy 的模型开关**（`COOKIES_STRATEGY_REAL_PROVIDER_ENABLED`
  和 `TextModelAlias`）。想单独关掉素材洞察的提取而留着策略生成，现在做不到，两者应当
  分开配。本地默认是 `deterministic`，所以这条链路在本地只验到「失败也会完整留痕」，
  真实模型调用要等凭据接入。
- 提取是同步的，一次一条。批量提取、失败重试、限流都没有；`insight_analysis_runs`
  的结构支持排队，但没有队列。

### 7.7.8　第 10 批：实验中心（2026-07-29）

而事实是功能根本不存在。这是 22 §8.3 要处理的同一类问题：可见的界面不能暗示不存在的
能力。所以换成一页明确写着「实验能力尚未启用」的说明。

**页面写三件事**：现在已经能做的（变体对比 → 投后分析 › 素材对比；驱动因素 →
投后分析 › 驱动因素，两者都已经在跑）、缺的是什么（Experiment / Variant / SampleCheck）、
以及为什么这两件不能互相顶替。最后一件是这一页真正的内容：**事后认出来的对比和事先
设计的实验，算出来的数字可以一模一样，但能支撑的说法不同**。事后对比是从已投素材里
挑出「只差一个变量」的一对，而这一对本来就是被人选出来投的，选择效应排除不掉——所以
AM-009 最多说到「可归因于这个变量」，再往前的因果说法它撑不住。这一层如果不写在页面上，
使用的人会把「可归因」直接当成因果读。

**AM-009 变体分析本身已经实现**（`performance.go:58` `VariantVerdict`：
attributable / directional / confounded / low_sample / no_features），在投后分析 ›
素材对比里出数，见 §7.7.5。所以这一页说「缺实验能力」时，指的是事先设计那一半，
不是对比算法那一半。

同批登记冲突 12 并按文档改了导航（四个视图 → 五个）。

**遗留：** 这一页是纯静态说明，不请求任何接口。真要开实验能力，从建 Experiment 对象
和「投放前登记假设」的表单开始，而不是从这一页往下加标签。另外，眼下比实验更靠前的
缺口是真实投放数据接入——没有平台侧的实际投放，实验也只能对着模拟数据跑。

### 7.7.9　第 11 批：系统设置（2026-07-29）

`internal/systems/insights/settings.go` + `src/components/InsightSettingsPage.tsx`，
端点 `GET /api/insights/v1/projects/{project_id}/settings`。**整页只读，一张表都不建。**

**它解决的不是「让人改阈值」，是「让人知道阈值是多少」。** 20 §121 给 MVP 的定位是
「可采用保守默认值」，22 §239 记的问题是「缺少实际阈值影响说明」。在此之前，决定
页面上什么时候说「充分」、什么时候说「样本不足」、什么时候干脆不给结论的那 19 个数字，
散在 `connectors.go` / `performance.go` / `operations.go` / `quality.go` / `prelaunch.go`
五个文件里，除了读源码没有任何地方看得到。**一个看不见的阈值和一个错的阈值，
在使用者那里是同一种东西。**

**为什么只读。** 03 §17.3 把「最低样本由全局规则还是行业模板配置」列为**待确认**。
在那条定下来之前开放写接口，等于先替它选了「全局规则」这个答案。`connectors.go:263-265`
的既有注释早就写着「等那条定了再挪到 系统设置 · 样本门槛」——这一页就是那些常量在等的地方。
页面上也没有禁用态的输入框：画一个改不动的框，会被读成权限不够，而不是功能没做。

**不建表、现算**（同 §7.7.6 能力运营）。返回的每个值都是代码常量本身，不是副本。
为此把 `performance.go` 里三个内联数字提成具名常量（`minTrendDays` / `minAnomalyDays` /
`anomalyMADMultiple`，值不变），并用测试锁住「页面显示值 == 代码常量」——抄一份迟早
和代码对不上，那时候这一页就从说明变成误导，比不做更糟。

**五组对齐导航的五个二级视图**：样本门槛（9 项）、观察窗口（6 项）已生效；
确认权限（4 项）说明三个 scope 各管到哪些接口，以及「确认前必须逐项复核」为什么
不可关闭；**通知与报告模板标成「未建设」并写明缺什么**——「还没做」和「做了但为空」
在设置页上必须长得不一样，通知尤其容易被误读成在后台默默生效，而代码里没有一处会
主动往外发消息。其中最要紧的是待复核堆积不会提醒任何人：人工复核是这套系统唯一的
质量闸门。

**实测修掉两处。** 一是通用页头给所有 `layout: 'settings'` 的页面挂了「保存配置」
按钮，点下去什么都不发生——会被读成「保存失败」而不是「不需要保存」，已按系统维度
去掉。二是「当前值与推荐不一致」的判定原先放在前端比字符串，确认权限那组两边说的是
不同的事（这个权限管到哪些操作 vs 该发给谁），字面永远不同，四条全部误报；改由服务端
出 `deviates` 字段，只对可比的数值项判定。推荐值一律写字面量而非由常量算出——算出来
它就永远等于当前值，「推荐」这个字段也就失去了独立含义。

**遗留：** 20 §121 与 22 §239 都写「仅管理员可见」，做不到——前端没有角色概念
（`navigation.ts` 与 `context/` 下都没有 role/admin），这一页对所有能进 Project 的人
可见。页面内容全是阈值说明，不含凭据也不含任何可写操作，所以现阶段的风险是「看到了
不该关心的东西」而不是「改了不该改的东西」；等权限模型引入角色再收口。

优先级归属、以及「谁拥有经验的最终确认权」这类问题，文档里明确标着未决，代码替它选一个

## 7.9 逐个入口验收发现（2026-07-30 起）

> 与 §7.7 的区别：§7.7 是建设者的自查，这一节是**验收方在真实环境上逐个入口跑出来的**。
> 每个入口一小节，按验收顺序追加。

### 7.9.1 投前洞察

**已修：假设类洞察卡在五个视图里一条都不显示。**
`已确认 + 类型=假设 + 无反例 + 置信=方向性` 的经验，原先策略证据（只收事实/统计观察）、
创意建议（只收建议）、风险与反例（只收有反例或置信偏弱的）三格都不收，整页一条不显示。
而这恰恰是从复盘默认沉淀出来的形态——`service.go` 的 `withCardDefaults` 在类型和置信留空时
就落到「假设 / 方向性」。修法是把假设类收进「风险与反例」，不新增第六个视图（03 §一级导航
把五个视图名定死了）。语义上也站得住：这一格收的是有边界的结论，「还没验证」是边界最大的一种。
空态文案一并改掉，原文案让人去别的视图找，而别的视图同样不收。

**未修，需先定夺：** AM-011 投后分析结果不自动成为洞察卡候选；22 §6.4② 引用到创意任务
只在经验上记引用、没写进创意任务；冷启动空页面不指路。

### 7.9.2 数据接入

**主干链路当面验证通过**（2026-07-30，`project_local`）：接入抖音数据源 → 未配字段映射时
启用按钮被替换成「先配字段映射」→ 配 5 个字段 → 启用 → 导 12 行 → 原样重导被内容哈希
拦下 → 3 个平台对象自动进「素材映射」待匹配队列，标注「花费计入总盘但不算到任何素材头上」。

**但导入这一步是坏的（2026-07-30 当面查库发现，P0，未修）。**

界面报告「提交 12 / 入库 12 / 被拒 0」，查库发现 12 行里 `impressions`、`clicks`、
`spend_cents`、`revenue_cents` **全是 0**，只有 `conversions` 有值。

| 缺陷 | 位置 | 内容 |
| --- | --- | --- |
| A 配的字段映射根本不用 | `DataConnectionsPage.tsx:608` `parseMetricCsv` → `canonicalColumn` | 解析表头只走前端**硬编码**的 17 条 `columnAliases`（`:642`），从不读数据源存的 `field_mapping`。`field_mapping` 只被当作「这个源准不准导入」的闸门，配的内容本身在解析时被无视 |
| B 认不出的列静默填 0 | `DataConnectionsPage.tsx:667` `toInteger` | 列名没匹配上 → 取不到值 → 返回 0 → 入库 → 界面报「被拒 0 行」。**假装成功的静默数据损坏，且损坏的是花费**。实测「曝光量」不在硬编码表（表里只有 曝光/展现/展现数）、「消耗(分)」也不在（表里是 消耗分，无括号），于是全变 0；「转化数」恰好在表里所以对了 |

上一版本条目把这条链路记成「证明字段映射真在做转换」，**该结论错误**，依据是界面回执而非库里的值。

**Raw 层：列和后端链路都在，前端导入路径不填。**

| 项 | 内容 |
| --- | --- |
| 文档要求 | doc10 §4 四层 Raw → Normalized → Canonical → Snapshot；MVP⑤「指标能回溯平台原字段」 |
| 现状 | `insight_metric_daily` **有 `raw` json 列**，Go 侧 `MetricRow.Raw` 一路透传到 `mysql_connector_repository.go:242` 落库；是前端导入时从来不填，实测全表 `raw IS NULL` |
| 后果 | 能回溯到「哪个批次导的」，回溯不到「平台报表上原来那行长什么样」 |
| 何时会疼 | doc10 §7 对账、口径纠纷、字段映射改错后的重算——三者都需要原始行才能查 |
| 补法 | 前端解析时把整行原始键值塞进 `row.raw`，**不用建表、不用改后端** |

**文档待更新：五个视图名与 §7.7.2 的记录不符。**
§7.7.2 记的是「数据源 / 接入向导 / 字段映射 / 导入批次 / 同步记录」；实际实现是
「数据源 / 导入任务 / 字段映射 / **素材映射** / 同步记录」。接入向导改成了右侧常驻表单，
多出来的素材映射正是 §2.3 第 2 条（AM-003）的硬要求。**改动方向是对的，是文档没跟上。**

**真缺口：Raw 层未落地。**

| 项 | 内容 |
| --- | --- |
| 文档要求 | doc10 §4 四层 Raw → Normalized → Canonical → Snapshot；MVP⑤「指标能回溯平台原字段」 |
| 现状 | 导入直接落 Canonical（`insight_metric_daily`），平台报表的原始行转换后即丢弃 |
| 后果 | 能回溯到「哪个批次导的」，回溯不到「平台报表上原来那行长什么样」 |
| 何时会疼 | doc10 §7 对账、口径纠纷、字段映射改错后的重算——三者都需要原始行才能查 |
| 补法 | 导入时按批次落一张只增的原始行表，不动现有 Canonical 链路 |

这一条**与平台接入无关，现在就能补**。（对账本身要等真实数据，Raw 层不用等。）

**五种接入方式里只有「文件导入」是实现了的。** `connectors.go` 的五个 `IngestMode` 是裸枚举，
选「官方 API」能注册成功但永远不会有数据进来：没有 OAuth 流程、没有拉数客户端，
`credential_ref` 也只是一个普通字符串列——**没有任何代码拿这个引用键去密钥服务换真凭据**，
`vault://` 只出现在测试和前端占位符里。doc10 §9 的「凭据不进业务库」这半边做到了
（`looksLikeSecret` 拦截），另半边（密钥服务本身）还不存在。

**仍挂着：** 路由冲突 3（03 = `/insight/data-sources/*`，代码 = `connections`）未定。

#### 缺陷 1：人工填写的特征进不了投后分析（P0，未修）

`ContentAnalysisPage.tsx:424` 的「保存人工结论」按钮，无论是**改写 AI 结论**还是
**AI 根本没提过、人第一次填**，一律走 `onReject` → `review_state: 'rejected'`。

而 `performance.go:388` `assignFeatures` 是这样过滤的：

```go
if !ok || feature.ReviewState == ReviewRejected {
    continue
}
```

**这里不看 `source`。** 注释写的是「被拒绝的 AI 行直接丢掉」，代码丢的是所有
rejected 行，人工那一行一样丢。`operations.go:433`（提取准确率）和 `:819`
（AI 与人工一致性）也按同一个值判。

后果：**在页面上手工填的特征，投后分析的素材对比与驱动因素一条都看不见**——
只有点过「认可」（`confirmed`）的才算数。演示脚本写的是 `confirmed`，所以驱动因素
能出数；换成人在界面上填，同样的数据就算不出来。

顺带一个措辞问题：零个 AI 结论时页面写「人工 · … · 推翻 AI」，素材状态说明写
「人工推翻并改写 AI 提取结果」，都不成立。

修的方向是把「有 AI 结论且人不同意」和「人工首次填写」分成两个 review_state，
而不是在 `assignFeatures` 里加 source 判断——后者会让「人工明确否掉某一项」失效。

#### 缺陷 2：AM-004 只有登记，没有识别（未修）

03 AM-004 与 MVP① 要求「先分清是六类中的哪一类」。现在页面上是六个
「判定为 X」按钮，`identifyType` 固定传 `source: 'human'`。后端
`IdentifyAssetType` 支持 `source: 'ai'` + 置信级别（`assets.go:364` 还强制
AI 来源必须带置信），但**代码里没有任何地方会以 AI 身份调它**——`extraction.go`
只写特征，不判类型，AI 那条分支只有测试在走。所以「识别」这一步实际是人做的，
`asset_type_source = ai` 的显示分支永远不会出现。

### 7.9.6 实验中心

**五个视图当面确认：共用同一屏说明**（2026-07-30）。切「实验列表 / A/B 变体 /

**这一页是本模块唯一「明说自己没做」的功能入口**（系统设置是只读页，性质不同）。

（事后从已投素材里挑出「只差一个变量」的一对，排除不掉选择效应，最多说到
「可归因于这个变量」；事先实验把变量、分组、门槛在看到结果前定死，才够得上因果说法）。

**验收结论：这一页现在的形态是对的，不需要修，需要的是建。** 22 §234 定的是
「P1 再开放；先建立 Experiment、Variant 和 SampleCheck 对象」，三个对象一个都还没有。

**要建成什么样（承 §7.9.5 的归属判定）：**

| 对象 | 存什么 | 谁写 |
| --- | --- | --- |
| Experiment | 假设、控制哪些变量、只改哪一项、观察窗口、样本门槛 | 人在页面上填 |
| Variant | 每组的取值、哪组是基线、哪些素材属于这一组 | 建实验时定，素材交货后挂入 |
| SampleCheck | 每组实际条数/天数/曝光，够不够事先定的门槛 | 系统按投放数据现算 |

门槛必须**事先**登记在 Experiment 上——事后再定门槛等于允许「凑够了就说显著」。

链路四段里 ①设计 ④判归因在本模块内，②交给创意创作生产是跨模块（先做成

**要建成什么样：报告的五个数据源，四个在本模块内**

20 §118 定了报告中心的性质：「单次分析可直接查看，跨团队沟通和周期复盘需要报告」，
价值是「将分散分析**组织**成可传播决策材料」。**它不产生新分析，它组织已有分析。**
AM-015 的四块内容照此拆解：

| 报告的一块 | 来源 | 位置 |
| --- | --- | --- |
| 素材表现 | 投后分析六视图的结论（素材对比、驱动因素、疲劳、异常） | 本模块 |
| 实验结论 | 实验中心（未建） | 本模块 |
| 经验 | 经验库里与本轮相关的已确认经验——这轮是印证了还是推翻了 | 本模块 |
| 下一轮建议 | 上面三块推出来的 | 本模块 |
| 投放元数据 | 哪次执行、数据窗口、创意包、花费口径、币种 | 投放模块 |

现在的实现只取了第五项，前四项一项都没取。

**本模块要做的处理是三件，都不是数据加工：**

1. **选择**——哪些结论值得进报告。数据清洗在数据接入那一层，强度判定（可归因 / 相关 /
   混杂）在投后分析已经算完，报告中心不重算，只挑。
2. **定格**——报告存的是「在这个时点、基于这份数据窗口、做了这个判断」。投后分析是活的，
   今天打开和下周打开数字就不一样；报告是要被引用、被追溯的，必须固化，不能实时现算。
   这是报告中心和投后分析在数据处理上唯一的本质差别。
3. **可重算出新版本**——03 §325：「指标或特征体系变更后支持重算，**不静默改写历史报告**」。
   重算产出新版本，旧版留着。这两条是一体的：能重算，但改不了旧的。

**一处文档没定、需要拍板的：自动带入还是人工挑。**

03 与 20 都没说报告的发现是系统自动汇总还是人工筛选。建议**自动带入 + 人工删减**：
投后分析已经给每条结论标了强度，报告可按强度自动带前几条，人再删。全靠人挑等于把
复盘成本又还回去，与 20 §118「降低复盘成本」相悖。此条登记为待确认项。

## 7.10 验收收口与修复顺序（2026-07-30）

**验收范围：** 8 个入口逐个当面走完（§7.9.1 ~ §7.9.8）。数据质量、能力运营、系统设置
三个治理页用户决定跳过——「和整体闭环没什么关系」。

### 最要紧的结论：这条闭环是两条不相交的线

```
【线 A】数据接入 ──┐
                   ├─→ 投后分析（六视图）─→ 到此为止
    内容分析 ──────┘

【线 B】投放模块的指标快照 ─→ 报告中心 ─→ 经验库 ─→ 投前洞察
```

投后分析读 `Connectors.ListMetricFacts` + `Assets.ListAssetFeatures`
（`performance.go:238`）；报告中心读 `Delivery.ReadExecution` 的快照
（`service.go:419`）。**两个入口读的不是同一份数据，中间没有任何连接。**

后果：前五个入口算出来的东西一步都流不到报告，经验库拿到的是人在输入框里手打的一句话。

### 修复顺序：倒着来

按导航顺序修会先修数据接入——但那条修完，数据仍然流不进报告，等于白干。

| 顺序 | 修什么 | 为什么排这个位置 | 记在 |
| --- | --- | --- | --- |
| 1 | **报告中心接到投后分析上** | 这一刀不修，后面所有修复都到不了终点 | §7.9.8 缺陷 1 |
| 2 | **内容分析的 `rejected`** | 人手填的特征进不了投后分析，修了 1 也没料可汇总 | §7.9.5 缺陷 1 |
| 3 | **数据接入的静默填 0** | 数字本身是错的（花费/曝光/点击/收入全 0） | §7.9.2 缺陷 A/B |

三条全在本模块内部，不依赖任何外部接入。

### 其余已登记缺陷（不阻塞闭环，可并行或延后）

- 投后分析「素材对比」整页白屏（`changed_features` nil→null），两端都要改 —— §7.9.3
- 短 ID 截断，分析素材库与经验库共 9+ 处 —— §7.9.4、§7.9.7
- 内容分析 AM-004 只有登记没有 AI 识别 —— §7.9.5
- 经验库详情面板只显示洞察卡九字段里的四个 —— §7.9.7
- 经验库 AM-013 六个检索维度全无、无详情路由、数据模型无复审日期 —— §7.9.7
- 报告正文不可编辑（20 §4.1）、无重算入口（03 §325） —— §7.9.8
- 两个误导性按钮：`MaterialInsightSurface` 的「创建 4 组测试素材」、
  工作台的「生成项目复盘报告」（写的是制品表，不进报告中心） —— §7.9.5、§7.9.8

### 开工前需要用户拍板的一件事

报告里的「发现」是**系统自动带入**还是**人工从投后分析里挑**？03 与 20 都没说。
建议自动带入 + 人工删减（20 §118「降低复盘成本」）。见 §7.9.8 末。
